# ETA / Theta 手机 Agent 插件架构设计草案

状态：v0.2 待评审，未实现。日期：2026-11-05。核对源码基线：`f49fa20`。

本次修订依据：Operit、Home Assistant、Pi、OpenClaw、DroidRun/Mobilerun 的官方仓库及文档调研。未安装运行这些项目，未做性能或成功率对比；参考链接与证据边界见第 15 节。

v0.2 替代 v0.1 的实施顺序：先验证外部能力无需修改 APK 即可接入、同服务多连接可区分且可停用，再迁移内置日历。此前“先做日历兼容路由”的建议不再作为下一步实施指令。本次仅审核并提交设计文档；第 16 节产品决策尚待确认，不授权实施业务代码。

本文中的新类、数据表、事件和错误码均为拟议接口，不代表现有功能。保留 Kotlin、Compose、现有多 Provider 接入与 Agent Runtime；不新增云服务依赖，不更换模型，不改包名。第一阶段只在现有 app 模块中划分包边界。

## 1. 目标与非目标

目标：ETA 是以手机为主要入口和本地执行端、通过插件扩展能力的个人 Agent。模型负责理解和选择工具；宿主负责工具目录、授权、执行生命周期与真实结果；插件负责具体能力。

第一版首先交付“能力连接与管理”，不是任意代码插件平台。主验收：外部开发者提供兼容现有客户端的远程 MCP 服务后，用户无需修改 ETA 源码、重编 APK 或安装可执行脚本，即可添加连接、发现工具、选择授权、调用、查看结果并停用。

同时验证：同一服务两个账户实例不混用凭据与工具；一个组合 Skill 能使用已授权工具但不能扩大权限；错误、断网、认证失效与停用状态可区分。日历作为后续原生兼容案例，而非证明外部扩展性的唯一案例。

内置扩展的次级验收仍保留：新增内置能力只需实现适配器并在组合入口注册，不为新工具修改 AgentLoop 或中央名称分支。内置新代码仍需发布 APK，不与远程接入的“无需重编”混淆。

第一版不做：插件市场、收费、下载执行 DEX/任意脚本、第三方 APK 协议、自动安装插件、iOS 移植、万能电脑执行端、全域数据隔离、所有操作 exactly-once。Skills 仍是指导内容和资源，不是代码沙箱，也不能授予权限。

## 3. 系统边界

调用关系（结构说明，不是部署新增服务）：

```text
对话 / 语音 / 分享 / 自动任务
    → 现有 Runtime / AgentLoop
    → 本轮工具目录与核心工具处理
    → PluginRoutingExecutor
    → 宿主策略 + 接纳门 + 必要确认
    → BuiltinAdapter 或 McpAdapter
    → 原有设备实现 / 远程 MCP 服务
    → ToolResult + 执行证据
    → 现有 transcript / 任务事件 / UI
```

三个概念必须分开：

- Plugin：实现某类能力的提供者，如内置日历。
- Connection：具体连接实例，如工作笔记服务和个人笔记服务；同一实现可有多实例。
- Skill：使用能力的方法、步骤和资源；其依赖只能提示缺少能力，不能启用插件或授予权限。

内置插件与宿主同进程，属于受信任应用代码，不构成隔离沙箱。MCP 服务是外部执行端，只能约束宿主发出的调用，无法通过本地开关撤销已经发生的远端效果。

### 3.1 用户看到的扩展形态

统一入口叫“扩展”，分为“内置能力”“已连接服务”“技能”三类。统一导航与状态说明，不强迫三类共用安装格式、生命周期或权限模型。

例如未来的“家庭助手”可由远程工具连接、睡前流程 Skill 和宿主配置表单共同构成；第一版分别配置并显式关联，不引入自动安装/授权的复合包。Skill 所需连接缺失时提示用户配置，不自行启用依赖。

### 3.2 第一版支持矩阵

| 形态 | 如何接入 | 执行位置 | 第一版范围 |
|---|---|---|---|
| 内置能力 | 随 APK 发布受信任适配器 | 手机 | 保留旧实现，后续逐组迁移 |
| 远程 MCP | 用户添加 endpoint 与现有支持的认证配置 | 外部服务 | 首要验证对象，复用现有 HTTP 客户端 |
| Skill | 沿用现有技能安装与加载流程 | 内容供模型使用；实际动作仍由工具执行 | 验证组合能力，不扩权 |
| 手机本地 MCP 进程 | 依赖 Node/Python/终端宿主 | 手机子进程 | 本版不实现；不是远程 MCP 的隐含能力 |
| JS/DEX/独立插件 APK | 需要新的代码运行与隔离协议 | 待设计 | 后续独立评估 |

无额外 ETA 云端控制服务。远程插件由其服务方部署；支持远程工具不等于数据留在手机。添加连接时说明任务参数会发往该服务。

### 3.3 核心职责约束

不新增一套多 Agent 编排引擎。结构化本地工具或服务 API 能可靠完成的任务优先直达；GUI 是补充路径，应用使用经验放在 Skill。沿用现有子代理，复杂任务才按需使用，不强制每项操作经过规划/执行双模型。

配置、连接状态、缓存和操作标识由宿主管理，不全部放入提示词。模型只获得任务所需的能力描述、明确连接别名和必要结果；凭据、重连次数等内部数据不进入上下文。

## 4. 插件身份、目录与契约

### 4.1 三层身份

- `pluginId`：稳定实现 ID，例如 `builtin.calendar`。
- `connectionId`：连接实例 ID；内置日历使用固定实例，MCP 复用现有 serverId。
- `toolId`：该提供者内部稳定工具 ID，例如 `create_calendar_event`。
- `modelName`：模型协议中的名称，由宿主维护映射。

现有内置名称和现有 MCP 名称算法不改变，不从 modelName 反向拆解原名。模型名称发生冲突时拒绝相关注册，绝不后注册覆盖前注册。`batch`、`tools_load`、子代理及会话控制工具名属于核心保留空间。

### 4.2 PluginManifest v1

这是宿主读取的声明，不直接将整个清单塞给模型。

| 字段 | 语义 |
|---|---|
| pluginId / displayName / description | 稳定身份和展示信息 |
| implementationVersion / contractVersion | 实现版本与宿主接口版本；v1 先采用精确接口版本兼容 |
| kind | BUILTIN / MCP；不在第一版暴露尚未实现的种类 |
| tools | 工具 ID、现有模型 schema、能力需求 |
| requestedCapabilities | 插件请求的能力，不等于已获授权 |
| configurationDescriptor | 非秘密配置字段及凭据引用类型 |

内置清单由受信任代码注册；MCP 清单由宿主根据已配置连接和发现结果生成。服务器的 description、annotations 都是不可信元数据，不作为宿主指令。

v1 的 PluginManifest 是宿主内部描述格式，不要求现有 MCP 服务额外实现 ETA 私有 manifest；不新增 ZIP 安装器或插件仓库。对于 MCP，pluginId 可固定为宿主通用实现 `connector.mcp`，具体服务由 connectionId 和连接配置区分，不能把 URL 或服务自报名称当作可信实现身份。

配置借鉴静态清单模式：通过宿主已知的 schema 与字段提示生成表单，先校验再连接，不执行服务端提供的脚本。首版只支持当前 MCP 所需字段及现有认证方式；通用 OAuth、动态页面和任意 JSON Schema UI 都不在本版承诺中。秘密字段仅保存引用，配置 schema 校验也不替代工具执行边界的参数解析。

### 4.3 最小代码边界（接口规格，非已实现代码）

| 对象 | 接口职责 |
|---|---|
| PluginProvider | 提供 descriptor，按 run 打开受限执行会话 |
| PluginRegistry | 注册提供者、查重、生成不可变 RunToolBindings |
| PluginRunSession | 同步 execute(ToolCall): ToolResult；close 幂等 |
| PluginRoutingExecutor | 实现现有 ToolExecutor；按本轮 binding 路由，不按字符串前缀猜测 |
| PluginPolicy | 组合旧工具开关、插件状态、场景限制、系统能力和确认策略 |
| PluginAdmissionCoordinator | 管理连接代次、停用与调用接纳的先后顺序 |
| PluginRepository | 管理内置插件状态和授权；MCP 配置仍由原仓库持有 |
| PluginCatalogProjection | 生成模型目录与插件 UI 的各自视图 |

`PluginRunSession` 第一版保持现有同步协议，不趁此重写所有工具为 suspend。耗时操作继续在 Runtime 工作线程执行；禁止在主线程等待网络/数据库。close 对正在进行的 I/O 做尽力取消，不能将关闭视为回滚。

### 4.4 运行上下文

由宿主创建并绑定 runId、conversationOwner、连接 ID、执行来源、取消/暂停信号及必要服务句柄。插件不得通过模型参数自行指定身份、账户、授权代次或权限范围。

第一版只接入内置代码与 MCP，因此不暴露第三方可获得完整 Android Context、数据库或凭据仓库的 SDK。未来独立 APK 插件使用另一套 IPC 受限接口，不把本进程内部接口原样公开。

## 5. 权限和执行接纳

### 5.1 权限取交集

可执行 = 本轮目录绑定有效 ∩ 插件启用 ∩ 单工具启用 ∩ 旧工具组开关 ∩ 当前入口约束 ∩ 所需系统能力 ∩ 本次必要确认。

新插件不能通过注册绕过：自动任务限制、角色会话只读限制、子代理继承限制、主屏确认、共享交互租约、工具暂停与取消。

系统授权、插件启用、操作确认是不同层。安装插件不会自动申请 Android 权限；模型工具也不能修改自己的授权。

### 5.2 停用的精确定义

第一版的插件停用含义：关闭该插件提供的直接工具入口。它不等于禁止整个 Agent 通过终端、浏览器或 GUI 接触同类数据。UI 应明确这一边界，不宣称全域数据隔离。

目标语义：

1. 停用与调用接纳在同一个连接级协调器串行排序。
2. 停用先成功：后续调用全部拒绝，含已排队但未接纳的调用。
3. 调用先接纳：标为已接纳/进行中，尽力取消，不承诺阻止已发送或已开始的副作用。
4. 停用确认返回前持久化状态并更新代次；写入失败保持内存拒绝态并明确报错，不能 UI 假显示成功。
5. 新启用能力从下一次 run 生效；本轮停用立即拒绝后续接纳。不在带签名历史中移除/改写已有 schema。
6. 重新启用不使旧快照复活；旧代次调用需新 run。

协调器只锁短时状态与接纳，不在持锁期间等待网络或用户确认。确认结束后再次检查 run、权限、参数摘要和连接代次。

MCP 目前是 run 快照权限，实施上述语义是新增行为，不是已有保证。连接 URL、认证方式、凭据或重要工具定义更新时也增加代次，旧绑定不静默切换目的地或账户。

### 5.3 确认策略

- 内置工具的操作类型由受信任代码声明；不是由模型或服务端自报。
- MCP `readOnlyHint` 只是提示；未知远端工具默认串行，启用时展示其外部执行属性。
- 远端工具采用 D2 已确认的“按工具授权自动执行”：授权限定到 connectionId＋toolId，并绑定工具定义摘要与授权代次。符合授权目标和运行场景的调用不因属于写操作而逐次弹窗；未授权不执行，工具授权不等于整连接授权。
- 自动执行仍需经过当前接纳检查；撤销立即阻止后续接纳，重要定义或账户变化需复核授权，目标含混仍需澄清，UNKNOWN 结果不盲目重试。前台授权不能隐含扩大为任意后台执行权限，后台入口仍须符合其策略。
- 不把迁移所有既有工具与全面改变确认体验绑在同一补丁中；D2 不取消既有主屏审批，也不改写以下内置日历的独立里程碑。
- 日历写入的逐次确认作为单独里程碑实现：展示操作、日历、时区、时间、提醒及待修改/删除对象。确认绑定 run、工具、规范化参数摘要、目标连接代次及有效期；参数变化需重确认。
- 后台/无 UI 来源不自动弹阻塞对话框。P5 引入逐次确认后，需要确认但当前入口无法承载的日历写入返回 APPROVAL_REQUIRED，不暗中允许无人值守；P0–P4 不提前改变既有日历确认行为。
- 拒绝、过期和取消不自动重问；模型也不得通过换一个工具名称继承原确认。

## 6. 目录冻结、懒加载与版本

- 同一 run 冻结工具身份、schema 和映射；权限在执行时检查。
- 保留 AgentLazyToolGroups 的追加式加载策略；优先沿用既有分组，后续添加插件分组。
- 不在第一版改写所有 Provider 的上下文策略。目录能追加的时机仍受现有 Provider 签名/历史约束控制。
- MCP 保留现有发现预算、运行工具上限和结果大小限制；管理页必须显示有多少工具因预算未进入本轮，不承诺全部可用。
- 刷新新增工具默认关闭；同名但 schema/权限语义变化的工具应标记待复核，不因名称相同而继承新的能力授权。以稳定字段的规范化摘要比较，描述变更也需展示差异。
- 基础 v1 不做依赖自动安装。缺插件返回明确缺失状态。

## 7. 结果、事件与恢复

### 7.1 保留已有 ToolResult

保留 content、images、sensitive、stop、executionSkipped、durationMs 的既有合同。可信 stop 只能由宿主适配器设置，不能从远端 JSON 同名字段转换。executionSkipped 当前由 Loop 管理；插件接纳拒绝需要扩展 Loop 与路由之间的可信结果约定，不能让第三方随意写该标记。

第一阶段不重包旧 JSON 结果，避免破坏成功判定与展示逻辑。执行证据通过宿主事件/账本保存，原始秘密不进入日志。既有 sensitive 只限制参数/工具原始结果持久化，不保证模型最后正文不会复述其中内容；UI 和文档不能承诺自动全面脱敏。

### 7.2 操作状态（宿主账本，不等于模型输出）

```text
PREPARED → WAITING_APPROVAL → ADMITTED → IN_FLIGHT
    → SUCCEEDED / FAILED_NO_EFFECT / UNKNOWN
未接纳之前可进入 REJECTED / CANCELLED_NOT_STARTED
```

只读操作可以直接由 PREPARED 进入 ADMITTED。网络超时、进程退出、写后回读失败不能一律记为 FAILED_NO_EFFECT；有副作用可能则 UNKNOWN。取消发生在执行中也不能宣称“未执行”。

账本记录：operationId、runId、父子调用关联、connectionId、toolId、绑定代次、状态、脱敏证据摘要和时间。需要恢复核查的事件 ID 等最小证据单独加密保存；无必要不保留原始参数。

### 7.3 幂等边界

- operationId 由宿主创建，不能仅用每次可能变化的模型 callId，更不能用标题/时间相同就推断重复任务。
- 同一已确认操作的传输重试复用 operationId；新一轮同文本请求不是自动同一操作。
- 本地账本与系统 Calendar Provider 不属于一个事务，不能承诺 exactly-once。
- 日历写入已返回 ID：按 ID 核验，返回已有证据，不重建。
- 写入已发生但 ID 未能持久化：UNKNOWN，停止自动重试；搜索近似事件只能作为核查线索，不作为唯一性证明。
- 普通 MCP 不假设支持幂等键；只有明确且经过实现验证的服务合同才允许自动重试写操作。
- 本地取消 HTTP 不代表远端终止。已有 MCP 传输重试行为需要在接入里程碑核对，未知写操作不得因插件层重试而叠加重复调用。

### 7.4 生命周期

Runtime 拥有 run session；插件路由不得重复 close 共享的 AgentLocalTools。迁移期各内置 wrapper 是非拥有型借用，统一由 Runtime 清理一次。MCP 客户端仍按 run 管理并保留同连接串行限制。子代理不增加权限，不创建独立拥有同一设备资源的执行器。

### 7.5 连接实例生命周期

借鉴 Home Assistant 的实例管理，但不引入其实体平台或常驻客户端架构。连接持久配置与 run 内客户端分开；配置页面测试用临时客户端，结束后释放，不把一次测试成功等同于永久在线。

状态拆为独立维度，避免一个 enabled 布尔值承担所有含义：

| 维度 | 建议状态 | 持久化原则 |
|---|---|---|
| 用户意图 | ENABLED / DISABLED / REMOVING | 由连接配置持有 |
| 配置健康 | UNCONFIGURED / READY / AUTH_REQUIRED / INCOMPATIBLE | 记录配置及检查结论；凭据仍在秘密存储 |
| 连接活动 | IDLE / CONNECTING / CONNECTED / RETRY_WAIT / FAILED / UNLOADING / UNLOAD_FAILED | 活跃状态仅属本进程；重启后不得沿用 CONNECTED |
| 工具授权 | 无工具获准 / 部分获准 / 定义变更待复核 | 按工具与定义摘要持久化 |

规则：

- 停用先关闭接纳，再关闭该连接活跃客户端；清理失败显示 UNLOAD_FAILED，但保持禁用，不恢复接纳。
- 删除配置与停用不同。先阻止接纳，再尝试清理连接及凭据；清理失败留可重试的删除状态，不声称远端账号授权已经撤销。
- 重载先使旧代次失效，再加载新配置；旧 run 不转接到新账户。
- 临时连接故障可由受限退避处理初始化/发现，不借此重放 tools/call；首版最多自动重试 3 次，间隔 2/5/10 秒并加少量抖动，超出后人工重试。停用、认证失败与配置错误取消重试；服务端较长 Retry-After 不得被短间隔覆盖。
- 配置迁移失败显示明确错误，不覆盖旧配置；不通过自动重建连接悄悄改变 serverId。
- UI 可显示最后检查时间，不能将缓存目录存在表示为当前在线。

### 7.6 多账户与 Skill 连接选择

每个 MCP serverId 对应独立 connectionId、凭据引用、授权集合、代次和 run 内客户端。工作/个人两个实例即使 URL、工具原名相同，也生成不同模型名称，结果与历史均关联原 connectionId。

工具描述带用户设置的连接别名；别名只用于展示，不用作权限身份。用户没有指定连接且存在多个可写候选时，先澄清或使用用户显式保存的默认选择，不由模型猜账户。读请求也不自动合并多个账户，除非任务明确要求。

Skill 可描述所需能力并让宿主解析为已配置连接；v1 不新增复杂依赖求解器。缺连接、未授权或定义变化都提示用户处理；Skill 不能写入授权表、携带可复用确认票据或自动切换到权限更大的连接。

## 8. 存储与秘密管理

不要复制 MCP 配置建立第二事实源：

- MCP URL、协议、工具目录、启用集合仍在 mcp_servers；凭据仍由 McpSecretStore 保存。
- PluginRepository 对外提供统一查询视图，内部组合内置插件状态和原 MCP Repository。
- 内置新增 `plugin_states`：pluginId、enabled、settingsJson（非秘密）、revision、updatedAt。
- 插件逐工具授权新增 `plugin_tool_grants`：connectionId、toolId、grantMode、approvedDefinitionDigest、revision。
- 持久写入恢复里程碑才增加 `plugin_operations`；第一步不为尚不存在的恢复功能预建空框架。
- MCP 连接增加 revision 或等价权威代次字段；各更新必须经过统一协调入口，避免 UI 旧方法绕过。

数据库迁移显式版本化，旧工具组开关作为上限保留。首次迁移让已存在的内置插件继承旧可用性，不擅自打开原来关闭的能力；新增远程工具默认不授权。

MCP 配置和密钥存储不具备跨存储原子性，更新中应保持连接不可接纳，成功后发布新代次；失败恢复或明确停用，不能继续用未知账户状态。Hook/入口 IPC 只传调用请求和非秘密身份，凭据不进入 RemotePreferences、模型参数、导出日志。

权威状态留在 App Runtime 所属进程。若未来真的拆成多应用进程，必须新增有 UID 校验的 Binder 配置/接纳服务；不能把当前 Room Flow 或 SharedPreferences 当作跨进程即时撤销保证。

## 9. 验证案例：先外部接入，再内置兼容

### 9.1 外部开发者接入案例（首要验收）

准备一个符合现有 HTTP MCP 客户端协议的测试服务，提供文档列表/检索和创建草稿等小范围能力；支持两个测试账户以区分个人和工作空间。测试服务只是验收夹具，不成为 ETA 生产依赖，不用硬编码工具名称的专用 Kotlin 分支通过验收。

验证流程：

1. 用同一个 ETA 测试 APK 添加两个独立连接，配置分别保存在原 MCP 仓库。
2. 发现工具并查看定义；默认不授权新增工具，选择后调用。
3. 对个人/工作连接返回不同标记，检查请求、凭据及结果归属。
4. 测试服务增加一个工具，不改 ETA 源码和 APK；刷新后该工具待授权，获准后可用。
5. 修改工具定义、制造认证失败/短暂断网、执行中停用，核对状态和接纳边界。
6. 验证一个 Skill 组合两个已授权工具完成任务；缺连接或撤销工具时不扩权。

夹具必须覆盖协议和故障注入，不能代替真实第三方兼容性。发布验收另选至少一个不为 ETA 定制、协议兼容的真实 MCP 服务，记录版本、认证方式、支持工具及实测限制；不预设服务、账号或付费调用已获授权。当前尚未运行任何验收服务。

### 9.2 后续内置兼容案例：日历

pluginId：`builtin.calendar`。

保留现有工具名：list_calendars、read_calendar_event、search_calendar_events、create_calendar_event、create_calendar_events、update_calendar_event、delete_calendar_event。

### A：行为不变的接入

将七个工具的 schema 和 binding 纳入注册表。BuiltinCalendarAdapter 调用现有 AgentLocalTools 入口，因此继续经过设备开关、Root/普通权限、执行准备和敏感结果处理。未迁移工具保留旧适配器；日历名称从旧目录注册来源排除，禁止双路拥有或被拒绝后 fallback 到旧路由。

这一步是路由插件化，不声称已拆净日历实现。

### B：补齐产品闭环

分享入口及图片输入继续复用现有功能。模型提取字段后，宿主生成确认；时区/日期/日历有歧义时补充确认，不猜测默认日历。写入后复用 CalendarOperations 回读验证，返回事件 ID 和 verified。

日历写入确认与持久操作账本单独实现，不能宣称 A 已提供去重恢复保证。

### C：逐步移除中央名称分支

抽取受限 CalendarExecutionFacade，保留已有公共准备检查，注册表直接调用 facade。旧 AgentLocalTools 日历分支最终删除或仅保留委托到同一注册路由，不能存在绕过停用的第二入口。

第二个内置插件选不占共享 GUI 的小能力组，验证新增插件不改 AgentLoop；其具体选择不阻塞日历设计。

## 10. UI 与用户体验

保留现有工具说明页、MCP 页面和 Skills 页面；新增统一“扩展”入口，包含内置能力、已连接服务、技能三个分类，逐步合并导航，不一次替换所有页面。第一版优先做好已连接服务，不先做市场首页、排行、评分和下载统计。

用户主路径：添加连接 → 看懂能力 → 填写配置 → 测试连接 → 选择工具 → 在任务中使用 → 查看结果 → 停用或删除。导入/添加、配置完成、连接成功、工具授权分别展示，不把任一步当成全流程完成。

列表显示：连接别名、类型、启用状态、可用/已授权工具数、最后检查时间，以及缺少权限、待授权、需要重新认证或连接失败等具体原因。技能页仍展示内容与依赖说明，不伪造在线状态。不是简单红绿在线灯。

详情页显示：

1. 连接与配置：MCP 复用现有编辑/测试流程，秘密输入不回显原值。
2. 工具：分项启用、能力需求、已批准定义与新定义差异。
3. 执行：近期调用状态、耗时、脱敏错误、UNKNOWN 结果核查提示。
4. 生命周期：停用、刷新；内置插件不能卸载，远程连接可删除。

删除连接前说明进行中的调用只能尽力取消。拒绝删除/停用后不暗中重连。新 PluginUiState 不通过要求静态 requirements 的旧 ToolCard 管线。

中、英、繁中资源同步；新功能文案明确“关闭直接工具，不撤销已完成操作，不阻断其他通用工具”。

## 11. 错误合同（新增建议）

| code | 含义 | 自动处置 |
|---|---|---|
| PLUGIN_DISABLED | 当前连接/插件已停用 | 不重试 |
| TOOL_GRANT_REQUIRED | 工具未授权或定义变更 | 引导用户复核，不自动启用 |
| PLUGIN_BINDING_STALE | 连接或授权代次已变更 | 旧 run 不继续；由用户发起新 run |
| PLUGIN_INCOMPATIBLE | 接口版本不支持 | 不尝试加载 |
| PLUGIN_TOOL_CONFLICT | 模型名称/工具身份冲突 | 拒绝相关注册 |
| APPROVAL_REQUIRED | 需要本次确认但当前入口不可承载 | 返回明确状态 |
| APPROVAL_EXPIRED | 确认失效或参数变化 | 不执行旧动作 |
| OPERATION_UNCONFIRMED | 副作用可能发生、结果不确定 | 查询或人工核查，禁止盲目重放 |

旧设备错误码继续保留。重试由宿主基于操作性质决定，不因工具返回 retryable=true 就自动重试。

## 12. 实施切片及文件范围

阶段编号在 v0.2 重新定义，不能继续按旧版 P0/P1 的日历优先顺序执行。

### P0：外部接入基线与最小契约

范围：`agent/plugin/` 下身份、descriptor、registry、run bindings 及测试；以现有 MCP 工具为首批目录输入。建立第 9.1 节测试夹具和已有客户端兼容性基线，记录协议版本、工具上限与认证方式，不先迁移日历。

退出条件：工具身份、核心保留名和冲突策略有测试；普通 MCP 服务不需 ETA 私有 manifest；最小示例明确外部开发者与 ETA 宿主各自负责什么。未接入生产执行路径前不称为功能完成。

### P1：MCP 适配与双连接调用

范围：McpPluginAdapter、PluginRoutingExecutor、AgentRuntimeRunExecutor 组合入口；复用 McpRunContext、McpHttpClient 的协议与结果适配。内置工具继续经原执行器，不做不相关迁移。保留 serverId、名称算法、token 存储、预算和每连接串行约束。

退出条件：不改 APK 即可添加远端新工具；同一服务两个连接不混账户、凭据或结果；未知工具和失败不落到旧本地执行分支。此阶段仍是兼容路由，不承诺实时停用已完成。

### P2：连接管理、授权与真实停用

范围：原 MCP Repository 的权威更新入口、连接代次、工具授权定义摘要、admission coordinator；新增扩展 UI 投影与宿主配置表单。落实 D2 的连接内单工具自动执行授权，展示适用目标与运行场景，并支持撤销和定义变化复核。既有 MCP 页面复用，授权写入不能仅靠 UI 弹窗；暂不为内置能力预建无用途的 plugin_states。

退出条件：双连接分别启停，停用与接纳竞态可验证；重载、认证失败、断网、卸载失败分别展示；凭据更新失败保持不可接纳。达到这一阶段才公开新版实时停用承诺。

### P3：Skill 组合与外部服务验收

范围：复用 Skill 加载流程与扩展 UI，提供一个说明所需连接/工具的示例 Skill 和外部接入说明；不引入脚本运行时或自动依赖安装。验证已授权远端工具无需逐次确认、未授权工具不执行，以及授权撤销、定义变化、连接歧义、后台入口限制和任务取消。

退出条件：第 9.1 节夹具全流程通过，且至少一个非 ETA 定制服务完成兼容实测；逐项报告未支持的认证/协议/内容类型。P0–P3 构成第一版“能力连接与管理”的交付范围，不宣称通用写入恢复或任意代码插件能力。

### P4：内置日历兼容迁移

范围：AgentToolCatalog、AgentRuntimeRunExecutor 的组合入口、BuiltinCalendarAdapter，以及内置状态/授权投影需要的存储。必要时调整 AgentModelClient 的目录注入点；沿用旧 LocalTools 检查与资源所有权，保留 batch、tools_load、subagent 和角色记忆路径。开发回退只在新 run 选择旧路径，不双执行或在执行失败后自动 fallback。

退出条件：七个旧日历工具名称、schema 和结果不变，普通权限/Root 路径保持，能力开关不扩大；迁移本身不改变确认体验。日历不再是验证外部扩展性的代用品。

### P5：写操作确认与不确定结果恢复

范围：以日历为首个有副作用案例，新增绑定参数的确认和最小持久操作账本；所有受支持入口有明确行为，不只依赖 UI handoff 检查点。补进程死亡故障注入和重复恢复测试。只有有证据的服务合同才扩展远端写入幂等支持。

退出条件：截图→日历真机闭环；写后异常为 UNKNOWN，不重复创建；不把本地取消当作远端回滚。日历 facade 抽取、第二个内置能力和独立 APK 通道均作为后续独立范围，不阻塞 P0–P3。

每个切片按依赖顺序落地。更改之前重新检查工作区和基线，不覆盖其他本地修改。实现前按新阶段确认范围，本文件修订不等于授权开始实现。

| 外部新增工具（P1） | 同一 APK 发现并调用新工具，无工具名专用代码分支 |

| 子代理/自动任务/角色会话 | 不能扩大父级/入口既有权限 |
| 停用与接纳竞态 | 能证明一个明确先后顺序；已开始操作不假报未执行 |

| 取消、重复 close | 资源回收一次，不影响其他 run 的共享资源 |

| 日志/导出/IPC | token 不泄露，敏感原始结果不误入持久工具记录 |

## 14. 评审建议结论

采用“精简 Agent 核心 + 连接实例管理 + 内置能力/MCP/Skills 分类扩展”。先用 P0–P3 证明外部能力接入、双连接隔离、用户可控与 Skill 组合；P4 再迁移日历，P5 补写操作确认与恢复。第一版不需要任意代码插件或插件市场才能形成有用的扩展能力。

仍待验证：现有 MCP 客户端与选定真实服务的协议/认证/返回内容兼容性；现有各入口是否都能承载确认卡；目标 ROM 日历普通权限与 Root 路径实际表现；外部服务对取消、幂等和重试的真实语义。没有证据前保留明确失败/UNKNOWN 状态，不用提示词承诺这些能力。

### 关键决策记录

1. 先验证第三方接入，不以迁移内置函数替代生态扩展性验收。
2. 管理以连接实例为单位；同一插件的两个账户不是一个授权主体。
3. 产品统一入口，协议和生命周期按形态区分；不做包格式大一统。
4. 静态描述与宿主表单优先，任意代码、UI 与 hooks 延后。
5. 核心不按业务扩张；Skill 说明方法，工具承担执行，宿主掌握授权与取消。
6. 以真实操作证据与故障测试验收，不以模型“完成”文本或其他项目宣传数字验收。
