# Theta 插件化改造方案

> 状态：v0.3，方案待确认，**未实现**。日期：2026-11-05。代码基线：`f49fa20`（main）。
>
> 来源：维护者的本地设计草案 v0.2（同日；调研了 Operit、Home Assistant、Pi、OpenClaw、DroidRun/Mobilerun 的官方仓库与文档），加上本次的源码复核、MCP 授权规范与外部服务核对。v0.2 不单独入库，其中仍然有效的规则已并入本文；本文是唯一有效版本。
>
> 文中的新类、数据表、事件和错误码都是拟议接口，不代表现有功能。本文入库不等于授权开工：每个里程碑开工前按 §16 确认范围。

## 0. 结论

**做什么**：把 Theta 做成"精简 Agent 核心 + 可插拔能力"的手机 Agent。模型负责理解任务、选择工具；宿主负责工具目录、授权、执行生命周期和真实结果；插件提供具体能力。

**怎么插**：第一版"可插拔"的主通道是 **MCP 连接**。远程服务和本机回环服务都走现有 HTTP 客户端，增删能力不需要改源码，也不需要重新打包 APK。手机原生能力（日历、通知、GUI、终端……）继续由随 APK 发布的内置代码提供，以后逐组接入同一套注册与管理。任意代码插件（DEX/JS/独立 APK）和插件市场不在第一版。

**先后顺序**：

| 里程碑 | 内容 | 用户可见收益 | 工作量 |
|---|---|---|---|
| M1 | 插件路由 + 两个现存安全缺口 | 自动任务不能再无约束地调用 MCP；远端悄悄改了工具定义，要重新批准才能用 | 中 |
| M2 | 连接管理与实时停用 | "扩展"入口；连接状态看得懂；停用立即生效；MCP 工具按连接懒加载 | 大 |
| M3 | Skill 组合 + 真实服务验收 | 一个技能串起多个连接；拿真实的第三方服务实测 | 小 |
| M4 | MCP OAuth 2.1 | 能连接需要 OAuth 登录的主流远程 MCP 服务 | 中 |

M1–M3 构成第一版"能力连接与管理"，M4 开始扩大能力范围。内置能力迁移、写操作确认与恢复、本机 stdio MCP、Theta 作为 MCP 服务端等列为后续方向（§13.5），按需排序。

**与 v0.2 的主要差异**（理由见 §1）：

1. 六个阶段压成四个可以单独发版的里程碑，取消只建框架、不接生产的 P0。
2. 新增两个 M1 必修项：自动任务的限制没有覆盖 MCP；工具定义变化后，授权仍按名称沿用。两者都是现有代码里的缺口，不是假设。
3. 新增数据外发策略（§6）。
4. OAuth 从"本版不承诺"改为独立里程碑 M4，复用现有模型 Provider 登录的 PKCE 和回环回调代码。
5. MCP 授权只存一处：在 `mcp_servers` 上扩展，不新建与它重复的授权表。
6. MCP 工具按连接懒加载，目录大小不随连接数线性增长。
7. 写明"本机回环 MCP"这条零代码过渡路径及其风险。

## 1. 对 v0.2 的评审

### 1.1 保留

v0.2 第 2 节引用的 14 处源码位置在 `f49fa20` 上逐一核对，全部属实（见 §3.1）。以下判断全部保留：

- 第一版交付"能力连接与管理"，以"外部服务不改 APK 即可接入"作为可插拔的验收标准，不用迁移内置函数来代替。
- Plugin、Connection、Skill 三个概念分开。授权主体是连接实例，同一服务的两个账户互不串用。
- 可执行权限取交集。新插件不能绕过自动任务、角色会话、子代理和主屏确认等已有限制。
- 服务端提供的 description 和 annotations 都是不可信元数据；`readOnlyHint` 不能作为并行执行或免确认的依据。
- 工具目录按 run 冻结（保护提示缓存和带签名的历史），权限在执行时检查。另外沿用 v0.2 的几条语义：停用的精确定义、接纳的先后顺序、"取消不等于未执行"，以及 `UNKNOWN` 结果。
- 复用同步的 `ToolExecutor` 和现有 `ToolResult` 合同，不借机改写成 suspend。
- 非目标：插件市场、收费、DEX 或任意脚本、第三方 APK 协议、自动安装、全域数据隔离、exactly-once。

### 1.2 修改

| 项 | v0.2 | v0.3 | 理由 |
|---|---|---|---|
| 阶段 | P0–P5 共六段；P0 只建注册表和夹具，不接生产 | M1–M4 共四段，每段可单独发版 | 个人项目的维护精力有限，不接生产的抽象层容易与真实需求脱节 |
| MCP 授权存储 | 启用集合留在 `mcp_servers`，另建 `plugin_tool_grants` | MCP 授权只存在 `mcp_servers`（新增定义摘要列）；内置插件需要时再建自己的状态表 | v0.2 自己要求不复制 MCP 配置；两处都记录"哪些工具可用"，就成了两个事实源 |
| 定义变更复核 | P2 | M1 | 现有代码刷新目录时按名称沿用授权，部分服务还会在运行开始时自动刷新（§3.2 第 4 条）。这是现存风险，修复成本低 |
| OAuth | 本版不承诺 | M4 | MCP 授权规范以 OAuth 2.1 为准，Home Assistant、GitHub 等主流服务默认走 OAuth（§9） |
| 懒加载 | 沿用现有分组，"后续添加插件分组" | M2 起每个连接一个懒加载分组 | MCP 工具目前一旦启用就常驻目录（单轮上限 64 个），连接一多就挤占上下文 |
| 日历迁移、写操作账本 | P4、P5 | 后续方向，按需排序 | 不影响第一版验收，v0.2 自己也写明不阻塞 P0–P3 |

### 1.3 新增

- **数据外发策略（§6）**。Theta 同时具备三个条件：能读私人数据、会接触不可信内容、能对外通信。接入远程连接会同时增加不可信内容和外发通道。v0.2 只把元数据当作不可信，没有处理"注入内容诱导后续调用把数据发出去"的情况。
- **本机回环 MCP 过渡路径（§4.3）**。
- **上游同步策略（§13.6）**：改名后同步上游的成本有变化。
- **Theta 作为 MCP 服务端**：列为后续方向。

## 2. 目标与非目标

**目标**：Theta 是以手机为主要入口和本地执行端、通过插件扩展能力的个人 Agent。

**第一版主验收**：外部开发者提供一个与现有客户端兼容的 MCP 服务后，用户**不改源码、不重编 APK、不安装可执行脚本**，就能完成：添加连接、发现工具、选择授权、调用、查看结果、停用。同时验证以下三点：

- 同一服务的两个账户实例不混用凭据、工具和结果；
- 组合 Skill 只能使用已授权的工具，不能扩大权限；
- 错误、断网、认证失效和停用这几种状态能区分开。

**次级验收**：新增一项内置能力时，只需实现适配器并在组合入口注册，不需要为新工具修改 `AgentLoop` 或中央名称分支。内置代码仍需随 APK 发布，这与"无需重编"是两回事。

**为什么以 MCP 为主通道**：

- MCP 是事实标准，现成的服务很多，自己的服务也能很快包一层。
- 服务在独立进程或独立机器上运行，崩溃和权限天然隔离，与语言无关。
- 新增能力不用重新发布 APK。
- MCP 服务是通过协议通信的独立程序，可以单独选择许可证（例如 MIT）开源，不必受 Theta 从上游继承的 PolyForm Noncommercial 约束（以许可证文本为准）。

**第一版不做**：

- 插件市场、收费；
- 下载执行 DEX 或任意脚本；
- 第三方 APK 协议、自动安装插件；
- iOS、万能电脑执行端；
- 全域数据隔离、所有操作 exactly-once。

Skill 仍然只是指导内容和资源，不是代码沙箱，也不能授予权限。

### 3.2 本次补充核对

1. **协议**：`McpHttpClient` 支持 `2026-07-28`（LATEST），以及 `2025-11-25`、`2025-06-18`、`2025-03-26`、`2024-11-05`（LEGACY），默认自动协商。JSON 和 SSE 两种响应都能读取。
2. **认证**：只支持 `none` 和 `bearer` 两种（`data/model/McpServer.kt`），没有 OAuth。
3. **命名**：模型看到的名称是 `mcp_<serverId 前 8 位>_<工具名>_<serverId 与工具名的摘要>`（`McpRunContext.kt:84`），已经按连接区分。同一服务的两个连接天然不会重名。
4. **定义变更**：刷新时授权按工具名沿用（`McpServerManager.kt:16`），不比较描述和参数 schema。刷新有两种：用户手动刷新；LATEST 协议的服务在目录过期后，由 `McpRunSnapshot.load()` 在**运行开始时**自动联网刷新并写回（`McpRunContext.kt:53`）。远端改了工具描述或参数后，用户看不到，下一次运行就按新定义调用。**这是现存缺口，M1 修复。**
5. **自动任务**：自动任务会拦截 `terminal`、`run_command`、`browser_use` 和建任务类工具。这个拦截写在 `AgentLocalTools` 的 `beforeToolExecution` 里（`AgentRuntimeRunExecutor.kt:207`）。而 `RoutingToolExecutor` 会把 MCP 调用直接交给 `McpToolExecutor`（`McpRunContext.kt:281`），不经过这层检查。结果是**自动任务可以无约束地调用所有已启用的 MCP 工具。这是现存缺口，M1 修复。**
6. **预算**（`McpToolLimits.kt`、`McpRunContext.kt`、`McpHttpClient.kt`）：
   - 发现阶段最多 512 个工具，目录总计 50 万字符；
   - 单次运行跨连接最多向模型暴露 64 个 MCP 工具，排在后面的连接的工具被丢弃；
   - 单次结果的文本和结构化内容各 64 KB，单张图片 2 MB，单次响应 1 MB。
7. **目录**：MCP 工具不属于任何懒加载分组，启用后常驻目录。现有分组只有 `personal_data`、`automation`、`skill_admin` 三个，是一张静态列表。
8. **并发**：MCP 工具不在 batch 的并行白名单里，按屏障逐个执行；每次运行中，每个连接复用同一个客户端。
9. **失败**：传输和协议异常统一归为 `MCP_CALL_FAILED`，不区分认证失败、超时和服务端错误。
10. **存储**：`mcp_servers` 表把工具目录和启用集合存成 JSON 列（`data/db/McpEntities.kt`）。数据库版本 29。
11. **明文 HTTP**：`network_security_config` 全局允许明文传输，MCP 地址只校验 URL 格式（`McpHttpClient.kt:524`）。因此 `http://127.0.0.1:端口` 和 Tailscale 内网地址都能直接作为连接地址。
12. **子代理**：有写权限的子代理档案可以使用本轮快照中的全部 `mcp_*` 工具（`agent/subagent/SubagentProfile.kt:56`），范围不会超出父 run。子代理的调用走父 run 的同一个执行器（`SubagentExecutor.kt:151`）。
13. **现有 OAuth 代码**：模型 Provider 登录已经实现了以下部分，M4 可以复用（都在 `agent/auth/`）：
    - PKCE（S256）；
    - 本机回环回调（`LoopbackAuthorizationReceiver.kt`）；
    - 刷新令牌和凭据存储。

## 4. 架构

### 4.1 调用关系

```text
对话 / 语音 / 分享 / 自动任务
  → 现有 Runtime / AgentLoop（可见性、batch 预检、取消、计时）
  → 本轮工具目录（冻结）+ 核心工具（batch、tools_load、子代理、会话控制）
  → PluginRoutingExecutor（按本轮绑定路由，不按名称前缀猜）
  → PluginPolicy（权限交集、入口约束、数据外发）+ 接纳门（M2）+ 必要确认
  → BuiltinAdapter（→ AgentLocalTools 的原有检查与实现）
    或 McpAdapter（→ McpHttpClient → 远程 / 本机回环 MCP 服务）
  → ToolResult + 执行证据 → 现有 transcript / 任务事件 / UI
```

内置插件与宿主在同一进程，属于受信任代码，不构成沙箱。MCP 服务是外部执行端：宿主只能约束自己发出的调用，没法用本地开关撤销已经在远端发生的效果。

### 4.2 三个概念

- **Plugin**：一类能力的实现方，例如内置日历、通用 MCP 连接器。
- **Connection**：具体的连接实例，例如"工作笔记"和"个人笔记"。同一个实现可以有多个实例；授权、凭据和结果都以实例为单位。
- **Skill**：使用能力的方法、步骤和资源。Skill 可以声明自己需要哪些能力，但不能启用插件，也不能授予权限。

界面上统一叫"扩展"，分成"内置能力""已连接服务""技能"三类。三类共用导航和状态说明，但不强求共用安装格式、生命周期或权限模型。

举例：一个"家庭助手"由 Home Assistant 连接和"睡前流程"Skill 组成。第一版里两者分别配置、显式关联，不做自动安装和授权的复合包。

### 4.3 第一版支持矩阵

| 形态 | 如何接入 | 执行位置 | 第一版范围 |
|---|---|---|---|
| 内置能力 | 随 APK 发布的受信任适配器 | 手机 | 保留旧实现，后续逐组迁移 |
| 远程 MCP | 填写 endpoint 和认证 | 外部服务 | 首要验收对象 |
| 本机回环 MCP | 在 Theta 的 Alpine/Debian 环境或其他 App 里启动 HTTP MCP 服务，按远程连接的方式添加 `http://127.0.0.1:端口` | 手机上的独立进程 | 过渡路径：不需要新代码，但 Theta 不管它的启停 |
| Skill | 沿用现有的技能安装与加载 | 内容给模型看，动作由工具执行 | 验证组合能力，不扩权 |
| 本机 stdio MCP | 宿主拉起子进程并管理生命周期 | 手机子进程 | 后续方向 |
| JS / DEX / 独立插件 APK | 需要新的代码运行与隔离协议 | 待设计 | 后续单独评估 |

**本机回环的约束**：

- 手机上任何 App 都能访问回环端口，所以服务**必须**要求 bearer token。
- 服务以 Theta 的 UID 运行（或以用户给的 root 运行），按"自有服务"对待。
- Theta 不保证它在线；连不上时照常显示为连接失败。

Theta 没有额外的云端控制服务。远程服务由服务方自己部署。支持远程工具不等于数据留在手机上，添加连接时要说明任务参数会发往该服务。

### 4.4 核心职责约束

- 不新增一套多 Agent 编排引擎。
- 结构化工具或服务 API 能可靠完成的任务，优先直接调用；GUI 是补充路径；应用的使用经验写进 Skill。
- 沿用现有子代理，复杂任务才按需使用。
- 配置、连接状态、缓存和操作标识由宿主管理，不放进提示词。模型只拿到任务需要的能力描述、连接别名和必要结果；凭据、重连次数等内部数据不进入上下文。

### 4.5 身份

- `pluginId`：稳定的实现 ID，如 `builtin.calendar`。所有 MCP 连接共用 `connector.mcp`。
- `connectionId`：连接实例 ID。内置插件用固定实例，MCP 复用现有的 `serverId`。
- `toolId`：提供者内部的稳定工具 ID，如 `create_calendar_event`；MCP 用服务端的工具原名。
- `modelName`：模型协议里的名称，由宿主维护映射。

身份规则：

- 现有内置工具名和 MCP 命名算法都不变，也不从 `modelName` 反推原名。
- 名称冲突时拒绝后注册的一方，绝不覆盖。
- `batch`、`tools_load`、子代理和会话控制工具属于核心保留名。
- URL 和服务自报的名称都不是可信身份。

### 4.6 PluginManifest v1（宿主内部格式）

| 字段 | 语义 |
|---|---|
| `pluginId` / `displayName` / `description` | 稳定身份和展示信息 |
| `implementationVersion` / `contractVersion` | 实现版本和宿主接口版本；v1 按接口版本精确匹配 |
| `kind` | `BUILTIN` / `MCP`；未实现的种类不暴露 |
| `tools` | 工具 ID、模型 schema、能力需求 |
| `requestedCapabilities` | 插件请求的能力，不等于已获授权 |
| `configurationDescriptor` | 非秘密的配置字段和凭据引用类型 |

- 内置清单由受信任代码注册。
- MCP 清单由宿主根据连接配置和发现结果生成。**MCP 服务不需要实现 Theta 私有的 manifest**，也不新增 ZIP 安装器或插件仓库。
- 配置表单由宿主按已知字段生成，先校验再连接，不执行服务端提供的脚本。
- 秘密字段只保存引用。
- 清单不会整个塞给模型。

### 4.7 代码边界（新增 `agent/plugin/` 包）

| 对象 | 职责 |
|---|---|
| `PluginProvider` | 提供 descriptor，按 run 打开受限会话 |
| `PluginRegistry` | 注册提供者、查重，生成不可变的 `RunToolBindings` |
| `PluginRunSession` | 同步的 `execute(ToolCall): ToolResult`；`close` 幂等 |
| `PluginRoutingExecutor` | 实现 `ToolExecutor`，替换 `RoutingToolExecutor`；按本轮绑定路由，未知名称不会落到本地分支 |
| `PluginPolicy` | 组合旧工具开关、连接状态、入口限制（自动任务等）、数据外发规则和确认要求 |
| `PluginAdmissionCoordinator`（M2） | 管理连接代次，把停用和调用接纳串行化 |
| `PluginCatalogProjection` | 分别生成模型目录和"扩展"界面需要的视图 |

插件代码集中放在新包里。对上游的热点文件（`AgentLoop`、`AgentLocalTools`、`AgentModelClient`）只改组合入口，以减少以后同步上游时的冲突。耗时操作继续在 Runtime 工作线程上执行，禁止在主线程等待网络或数据库。

### 4.8 运行上下文

宿主创建运行上下文，并绑定以下内容：

- runId 和会话归属；
- connectionId；
- 执行来源（交互、自动任务或子代理）；
- 取消信号和必要的服务句柄。

插件不能通过模型参数指定身份、账户、授权代次或权限范围。

第一版只接入内置代码和 MCP，不向第三方暴露 Android Context、数据库或凭据仓库。将来的独立 APK 插件另走带 UID 校验的 IPC 接口。

## 5. 权限、接纳与停用

### 5.1 权限取交集

一次调用只有同时满足以下全部条件才执行：

- 本轮绑定有效；
- 插件已启用；
- 该工具已授权，且定义未变；
- 旧工具组开关允许；
- 符合入口约束；
- 符合数据外发规则；
- 所需系统能力可用；
- 已取得本次必要的确认。

**入口约束（M1）**：

- **自动任务**：连接新增"允许自动任务使用"开关，默认关闭。关闭时，自动任务里的调用返回 `AUTOMATION_ACTION_UNAVAILABLE`（沿用现有错误码）。升级后，已有连接同样默认关闭；需要它的自动任务要手动打开。
- **子代理**：子代理的调用经过同一个路由，因此自动任务约束和外发规则同样生效。子代理只能使用父 run 已绑定的工具（现状如此，保持不变）。
- **其他既有限制**：角色会话只读、主屏确认、共享交互租约等照旧生效，新插件不能通过注册绕过。

系统授权、插件启用、操作确认是三个不同的层次。安装或添加插件不会自动申请 Android 权限，模型工具也不能修改自己的授权。

### 5.2 停用

插件或连接停用的含义是：**关闭它提供的直接工具入口**。这并不禁止 Agent 通过终端、浏览器或 GUI 接触同类数据，界面上要写明这条边界。

目标语义（从 M2 起对外承诺）：

1. 停用和调用接纳在同一个连接级协调器里串行排序。
2. 停用先成功：此后的调用全部拒绝，包括已经排队但尚未接纳的调用。
3. 调用先被接纳：标记为进行中，尽力取消，但不承诺能阻止已经发出或已经开始的副作用。
4. 停用返回之前，先持久化状态并递增代次。写入失败时保持内存中的拒绝状态并明确报错，界面不能假装成功。
5. 新启用的能力从下一次 run 开始生效。本轮带签名的历史不移除，也不改写其中的 schema。
6. 重新启用不会让旧快照复活；旧代次的调用需要新开一个 run。

其他规则：

- 协调器只锁短时状态，持锁期间不等待网络或用户确认。确认结束后，再次检查 run、权限、参数摘要和连接代次。
- 连接的 URL、认证方式、凭据或重要工具定义变化时，同样递增代次。旧绑定不会静默切换到新目的地或新账户。
- 现状（M2 之前）：MCP 权限是 run 快照，停用要到下一次 run 才生效。

### 5.3 确认策略

- 内置工具的操作类型由受信任代码声明，不由模型或服务端自报。
- MCP 的 `readOnlyHint` 只是提示。未知的远端工具默认串行执行，界面上展示它的外部执行属性。
- 需要确认的调用，确认要绑定 run、工具、规范化后的参数摘要、连接代次和有效期。参数一变就要重新确认。
- 用户拒绝、确认过期或调用被取消后，不自动重新询问；模型也不能换一个工具名来沿用原来的确认。
- 后台入口不弹阻塞对话框。需要确认但当前入口无法承载时，返回 `APPROVAL_REQUIRED`，不暗中放行。
- 不把"迁移所有既有工具"和"改变确认体验"放进同一个补丁。

### 5.4 工具定义变更（M1）

授权绑定的是**定义摘要**，而不只是工具名：把工具名、描述、输入 schema 和 annotations 规范化后计算摘要，授权时记录下来。

- 刷新后摘要没变：照常可用。
- 摘要变了：该工具标记为"定义已变更，待复核"，复核之前不进入目录。界面展示新旧定义的差异。
- 新发现的工具默认不授权（保持现状）。
- 升级迁移：已启用的工具在升级后第一次刷新时记录当时的摘要（首次使用即信任），之后的变化才需要复核。现有工具不会因为升级而失效。

## 6. 数据外发防护（新增）

Theta 同时具备三个条件：

- **能读私人数据**：短信、通知、通讯录、日历、文件。
- **会接触不可信内容**：网页、通知、分享进来的内容、外部服务的返回。
- **能对外通信**：远程 MCP、网页请求、通过 GUI 操作聊天软件。

三者同时存在时，注入的内容可以诱导模型把私人数据发出去（Simon Willison 称之为"致命三要素"）。接入远程连接会同时增加不可信内容和外发通道，所以插件化必须同时带上外发规则。

**连接信任级别**：添加连接时由用户选择。默认是"第三方服务"；回环地址和私有网段地址预选"自有服务"，用户可以改。

| 级别 | 适用范围 | 规则 |
|---|---|---|
| 自有服务 | 本机回环、用户自己部署的服务 | 视同本地工具 |
| 第三方服务 | 其他所有服务 | 受下列外发规则约束，返回内容视为不可信 |

自有服务如果会把参数转发到外部（例如代为抓取网页的代理），应标为第三方。

**运行内标记**：路由层能看到本轮每次调用的结果，据此维护两个标记：

- `sensitiveLoaded`：本轮读过敏感数据，即结果带 `sensitive` 标记，或调用过 `personal_data` 组的工具。
- `untrustedLoaded`：本轮接触过不可信内容，即调用过网页或浏览器工具、读取过通知、处理过分享内容，或拿到过第三方连接的返回。

**规则**：

- **E1（M1）**：在自动任务中，一旦 `sensitiveLoaded`，之后对第三方连接的调用一律拒绝（返回 `DATA_EGRESS_BLOCKED`）。后台没有人看着，宁可让任务失败。
- **E2（M1 只记录，M2 加确认）**：在交互会话中，`sensitiveLoaded` 之后第一次调用某个第三方连接时，M1 只把这两个标记写进审计事件；M2 有了确认通道后，改为逐次确认，展示连接别名和参数摘要。
- **E3**：第三方连接的返回在转录中标记为外部内容。这只是辅助手段，不能代替 E1 和 E2。

**边界**：这套规则只管插件提供的直接工具。终端、浏览器、带参数的 `web_fetch` 请求和 GUI 操作同样可能把数据发出去，这些是既有风险，本方案不声称覆盖。`web_fetch` 是否纳入同一规则，留到 M2 评估。

## 7. 目录预算与懒加载

- 同一 run 冻结工具身份、schema 和映射；权限在执行时检查。
- **从 M2 起，每个 MCP 连接对应一个懒加载分组**（例如 `mcp:家庭`），在开启"精简工具目录"时生效。
  - 加载器的描述只列连接别名、一句话说明和工具名；加载后追加完整定义。
  - 目录只增不减，不破坏提示缓存。
  - `AgentLazyToolGroups` 的静态分组表要改为每轮计算。
- 第一版不改写各 Provider 的上下文策略；什么时候能追加工具，仍受现有签名和历史约束。
- 保留现有的发现预算、单轮 64 个工具的上限和结果大小限制。界面要显示有多少工具因预算没进入本轮，不承诺全部可用。
- 参考数据：fork.3 时本地工具约 130 个，定义约 7.4 万字符（粗测），已经是上下文的大头。连接多了以后，不懒加载就撑不住。
- v1 不做依赖的自动安装。缺少插件时返回明确的缺失状态。

## 8. 结果、生命周期与恢复

### 8.1 ToolResult

- 保留 `content`、`images`、`sensitive`、`stop`、`executionSkipped`、`durationMs` 的既有合同。
- 可信的 `stop` 只能由宿主适配器设置，不能从远端 JSON 里的同名字段转换过来。
- `executionSkipped` 目前由 Loop 管理。插件接纳被拒绝时要用到它，需要扩展 Loop 与路由之间的可信约定，第三方不能随意设置。
- 第一阶段不重新包装旧的 JSON 结果，避免破坏成功判定和展示。
- `sensitive` 只限制原始结果的持久化，不能保证模型最后的回复不复述其中内容。界面和文档都不承诺自动脱敏。

### 8.2 连接生命周期

借鉴 Home Assistant 的配置实例管理，但不引入它的实体平台或常驻客户端。持久配置与 run 内的客户端分开。配置页的"测试"用临时客户端，用完即释放；测试成功不等于一直在线。

| 维度 | 状态 | 持久化方式 |
|---|---|---|
| 用户意图 | ENABLED / DISABLED / REMOVING | 随连接配置保存 |
| 配置健康 | UNCONFIGURED / READY / AUTH_REQUIRED / INCOMPATIBLE | 保存检查结论；凭据仍在秘密存储中 |
| 连接活动 | IDLE / CONNECTING / CONNECTED / RETRY_WAIT / FAILED / UNLOADING / UNLOAD_FAILED | 只存在于本进程内；重启后不沿用 CONNECTED |
| 工具授权 | 无 / 部分 / 定义变更待复核 | 按工具和定义摘要保存 |

规则：

- **停用**：先关闭接纳，再关闭该连接的活跃客户端。清理失败时显示 UNLOAD_FAILED，但连接保持禁用。
- **删除**（不同于停用）：先阻止接纳，再清理连接和凭据。清理失败时保留一个可重试的删除状态，不声称远端授权已经撤销。
- **重载**：先让旧代次失效，再加载新配置。旧 run 不会转接到新账户。
- **重试**：发现阶段的临时故障最多自动重试 3 次，间隔 2、5、10 秒并加少量抖动，之后改为人工重试。停用、认证失败和配置错误会取消重试。服务端给出的更长 `Retry-After` 不会被覆盖。**`tools/call` 永远不自动重放。**
- **运行开始时的刷新**：改为限时。超时或失败时跳过该连接，并在本轮界面上提示，避免一个慢服务拖住所有对话的开始（现状见 §3.2 第 4 条）。
- **配置迁移**：失败时显示明确错误，不覆盖旧配置，也不通过自动重建悄悄改变 `serverId`。
- **在线状态**：界面可以显示最后检查时间，但不能把"有缓存目录"显示成"在线"。

### 8.3 多账户与 Skill

**连接隔离**：每个 MCP `serverId` 有自己独立的 connectionId、凭据引用、授权集合、代次和 run 内客户端。两个实例即使 URL 和工具原名相同，模型名也不同（现有算法已经保证）。结果和历史都关联到原来的 connectionId。

**账户选择**：

- 工具描述里带上用户设置的连接别名。别名只用于展示，不作为权限身份。
- 用户没有指定连接、又存在多个可写的候选时，先向用户澄清，或者使用用户明确保存过的默认值，不让模型去猜账户。
- 读请求也不自动合并多个账户的数据，除非任务明确要求。

**Skill**：

- Skill 可以描述自己需要什么能力，由宿主解析到已配置的连接。
- 缺少连接、未授权或定义有变化时，都提示用户处理。
- Skill 不能写授权表，不能携带可复用的确认票据，也不能自动切换到权限更大的连接。
- v1 不做依赖求解器。

### 8.4 写操作与不确定结果

第一版（M1–M3）不建持久的操作账本，但保证两点：

- 已经发出的 MCP 调用遇到超时、断线或进程退出时，返回 `OPERATION_UNCONFIRMED`（"可能已执行，请核查"），而不是笼统的失败。这样模型不会盲目重试，造成重复写入。
- 插件层对 `tools/call` 不做任何自动重试，也不假设普通 MCP 服务支持幂等键。本地取消了 HTTP 请求，不代表远端已经停止执行。

完整的写操作确认与恢复放在后续方向"写操作确认与恢复"中实现，以日历作为第一个案例。内容包括操作状态机、由宿主生成的 operationId、写后崩溃恢复，规则沿用 v0.2：

```text
PREPARED → WAITING_APPROVAL → ADMITTED → IN_FLIGHT → SUCCEEDED / FAILED_NO_EFFECT / UNKNOWN
未接纳之前可以进入 REJECTED / CANCELLED_NOT_STARTED
```

本地账本和系统日历不在同一个事务里，不承诺 exactly-once。写入已经发生、但事件 ID 没能持久化时，记为 UNKNOWN 并停止自动重试；搜索相近的事件只能作为核查线索。

### 8.5 资源所有权

- Runtime 拥有 run 会话。插件路由不会再次关闭共享的 `AgentLocalTools`。
- 迁移期间的内置适配器只是借用资源，不拥有它们，由 Runtime 统一清理一次。
- MCP 客户端按 run 管理，保留同一连接的调用串行执行。
- 子代理不增加权限，也不创建独立占有同一设备资源的执行器。

## 9. 认证与 OAuth（M4）

目前只支持无认证和 bearer。能直接接入的服务有三类：

- 自建服务；
- 本机回环服务；
- 接受个人令牌的服务（例如 GitHub 远程 MCP 可以用 PAT 代替 OAuth）。

MCP 授权规范（2025-11-25）以 OAuth 2.1 为准，主流服务默认也走 OAuth。下表列出规范要求和 Theta 的实现要点：

| 要求（MCP 授权规范） | Theta 实现要点 |
|---|---|
| 必须使用 PKCE，方法为 S256；授权服务器元数据缺少 `code_challenge_methods_supported` 时必须拒绝继续 | 复用 `agent/auth/ProviderOAuthClient` 的 PKCE |
| 先通过受保护资源元数据找到授权服务器（优先用 401 响应 `WWW-Authenticate` 中的 `resource_metadata`，没有时查 well-known 地址），再获取 RFC 8414 或 OIDC 元数据 | 新增发现逻辑，结果按连接缓存 |
| 授权请求和换令牌请求都要带 `resource` 参数（RFC 8707，取 MCP 服务的规范 URI） | 新增 |
| 客户端注册的优先级：预注册 → Client ID Metadata Document → 动态注册 → 让用户手填 | 需要一个 HTTPS 地址来托管 Theta 的客户端元数据 JSON（§16 D3） |
| 回调地址必须是 localhost 或 HTTPS | 复用 `LoopbackAuthorizationReceiver`（本机回环），不用自定义 scheme |
| 收到 403 `insufficient_scope` 时做增量授权，并限制重试次数 | 新增；超过次数后标记 AUTH_REQUIRED |

令牌（包括刷新令牌）存进 `McpSecretStore`，不进入日志、导出、IPC 或模型参数。刷新失败的连接进入 AUTH_REQUIRED 状态，不会静默降级为无认证。

**验收目标**：Home Assistant 自带的 MCP Server 集成（`/api/mcp`）。它的文档写明使用 OAuth 2.0 + PKCE，支持 Client ID Metadata Document，不支持动态注册，正好覆盖这条路径。另外，HA 的长期访问令牌能不能直接作为 bearer 访问 `/api/mcp`，需要实测；如果可以，M3 就能先接入。

## 10. 存储与迁移

- 不复制 MCP 配置，不建第二个事实源。URL、协议、工具目录、启用集合和授权都留在 `mcp_servers`，凭据留在 `McpSecretStore`。
- `mcp_servers` 新增以下列。数据库版本从 29 升到 30，显式迁移，并配 Robolectric 迁移测试。

  | 列 | 内容 | 默认值 | 里程碑 |
  |---|---|---|---|
  | `approved_tool_digests_json` | 工具名 → 已批准的定义摘要 | — | M1 |
  | `trust_level` | `self_hosted` / `third_party` | `third_party` | M1 |
  | `allow_in_automation` | 是否允许自动任务使用 | false | M1 |
  | `revision` | 连接代次 | — | M2 |

- 以下表等到真正需要时再建，不预先搭空框架：
  - 内置插件的状态表（如 `plugin_states`，含 pluginId、enabled、非秘密的 settingsJson、revision、updatedAt），在内置能力迁移时建；
  - `plugin_operations`，随写操作恢复一起建。
- **升级迁移**：
  - 旧的工具组开关作为上限保留；
  - 原来关闭的能力不会因为迁移被打开；
  - 新发现的远程工具默认不授权。
- **跨存储一致性**：MCP 配置和密钥存储之间没有跨存储的原子性。更新期间连接不接纳调用，成功后才发布新代次。失败时恢复原状或明确停用，不带着未知的账户状态继续。
- **权威状态**：留在 Runtime 所属进程。将来如果真拆成多个进程，必须新增带 UID 校验的 Binder 配置与接纳服务，不能把 Room Flow 或 SharedPreferences 当作跨进程即时撤销的保证。

## 11. 界面

- **入口**：保留现有的工具说明页、MCP 页和技能页。M2 新增统一的"扩展"入口，分"内置能力""已连接服务""技能"三类，逐步合并导航。第一版先把"已连接服务"做好，不做市场首页、排行和下载统计。
- **主路径**：添加连接 → 看懂能力 → 填写配置（含信任级别、是否允许自动任务）→ 测试连接 → 选择工具 → 在任务中使用 → 查看结果 → 停用或删除。每一步单独显示完成状态。
- **列表**：显示连接别名、类型、信任级别、启用状态、可用和已授权的工具数、最后检查时间，以及具体原因（缺权限、待复核、需要重新认证、连接失败），不用简单的红绿灯。
- **详情页**：
  - 配置与测试，秘密不回显；
  - 工具的分项授权、能力需求和定义差异；
  - 近期调用的状态、耗时、脱敏后的错误，以及 `OPERATION_UNCONFIRMED` 的核查提示；
  - 停用、刷新、删除（内置能力不能删除）。
- 新的展示投影不走旧的 `ToolCard` 管线（它要求静态 requirements）。
- 中文、英文、繁体中文资源同步更新。文案要写明："停用只关闭直接工具，不撤销已完成的操作，也不阻断其他通用工具。"

## 12. 错误合同

| code | 含义 | 处置 |
|---|---|---|
| `PLUGIN_DISABLED` | 连接或插件已停用 | 不重试 |
| `TOOL_GRANT_REQUIRED` | 未授权，或定义已变更待复核 | 引导用户复核，不自动启用 |
| `PLUGIN_BINDING_STALE` | 连接或授权的代次已变 | 旧 run 不继续，由用户发起新 run |
| `PLUGIN_INCOMPATIBLE` | 接口版本不支持 | 不加载 |
| `PLUGIN_TOOL_CONFLICT` | 名称或身份冲突 | 拒绝相关注册 |
| `AUTOMATION_ACTION_UNAVAILABLE` | 自动任务不允许使用该连接（沿用现有错误码） | 不重试 |
| `DATA_EGRESS_BLOCKED` | 被外发规则拒绝（§6） | 不重试，提示改为交互执行 |
| `AUTH_REQUIRED` | 认证失效或缺少 scope | 引导用户重新登录 |
| `APPROVAL_REQUIRED` | 需要确认，但当前入口无法承载 | 返回明确状态 |
| `APPROVAL_EXPIRED` | 确认已失效或参数已变 | 不执行旧动作 |
| `OPERATION_UNCONFIRMED` | 可能已执行，结果不确定 | 核查，禁止盲目重放 |

`MCP_CALL_FAILED` 拆分成上面这些错误码，再加上超时、服务端错误等具体原因。旧的设备错误码保留。是否重试由宿主按操作性质决定，不会因为工具返回 `retryable=true` 就自动重试。

## 13. 里程碑

每个里程碑由一个或几个 PR 组成，合入 `main` 后按仓库约定构建（§15），可以单独发版。开工前重新检查工作区和代码基线。

### M1：插件路由 + 安全底线（中）

范围：

- 在 `agent/plugin/` 下实现身份、descriptor、`PluginRegistry`、`RunToolBindings`、`PluginRoutingExecutor` 和 `PluginPolicy`。
  - MCP 是第一个提供者：`McpPluginAdapter` 复用 `McpRunSnapshot`、`McpHttpClient` 和现有的结果适配。
  - 本地工具整体作为一个"旧路由"提供者，原样转发。
- `AgentRuntimeRunExecutor` 的组合入口改用 `PluginRoutingExecutor`。
- 自动任务约束覆盖 MCP（§5.1）。
- 按定义摘要授权（§5.4），含升级迁移。
- 外发规则 E1，以及 E2 的审计记录（§6）。
- 细分 `MCP_CALL_FAILED`，新增 `OPERATION_UNCONFIRMED`（§8.4）。
- 现有 MCP 页面增加：信任级别、"允许自动任务使用"开关、"定义已变更，待复核"的提示。
- 测试：
  - 注册、冲突和保留名；
  - 路由不会落到旧分支；
  - 自动任务拦截；
  - 摘要变化；
  - 外发规则；
  - 29 → 30 迁移；
  - 用 OkHttp 的 MockWebServer（需新增测试依赖）搭一个双账户的夹具服务，覆盖断网、认证失败和工具定义变化。

退出条件：

- 同一个 APK 可以添加两个夹具连接并分别调用，账户、凭据和结果互不串用；
- 远端修改工具定义后，该工具不可用，复核后恢复；
- 自动任务调用未放行的连接时被拒绝；
- MCP 失败不会落到本地分支；
- 现有的工具名、schema 和结果都不变。

### M2：连接管理与实时停用（大）

范围：

- 连接代次、`PluginAdmissionCoordinator` 和 §5.2 的停用语义；
- §8.2 的状态维度、重试和限时刷新；
- "扩展"入口，以及已连接服务的列表页和详情页（§11）；
- 每个连接一个懒加载分组（§7）；
- 交互会话中的外发确认 E2。

退出条件：

- 两个连接可以分别启停，停用与接纳之间的竞态可以测试；
- 重载、认证失败、断网和清理失败分别有展示；
- 凭据更新失败时，连接不接纳调用；
- 连接很多时，目录里只增加加载器条目。

达到这一阶段，才对外承诺"停用实时生效"。

### M3：Skill 组合 + 真实服务验收（小）

范围：

- 一个示例 Skill，说明它需要哪些连接和工具。宿主解析这些需求，缺失时提示用户。
- 一份外部接入说明，写给 MCP 服务开发者：Theta 支持的协议版本、认证方式和各项限制。
- 至少用一个不为 Theta 定制的真实服务做验收。候选：
  - GitHub 远程 MCP（PAT 作为 bearer）；
  - Home Assistant MCP Server（长期令牌作为 bearer，需实测；不行就留到 M4）；
  - 用户自己部署的服务（例如家里服务器上的只读运维接口）。

退出条件：§14 中标注 M1–M3 的场景全部通过；逐项记录不支持的认证方式、协议和内容类型。M1–M3 合起来就是第一版"能力连接与管理"。

### M4：MCP OAuth 2.1（中）

范围：按 §9 实现。复用 `agent/auth/` 里的 PKCE、回环回调和刷新逻辑；新增资源元数据发现、`resource` 参数、客户端元数据文档和增量授权。

退出条件：

- HA MCP Server 能通过 OAuth 连接并调用；
- 令牌刷新、撤销后重新登录、scope 不足，都有明确的状态；
- 令牌不出现在日志和导出中。

### 13.5 后续方向（按需排序，各自单独评审）

| 方向 | 要点 | 前置 |
|---|---|---|
| 内置能力迁移 | 以日历为第一例，七个现有工具的名称、schema 和结果不变。分三步：先经适配器调用 `AgentLocalTools`；再抽出 `CalendarExecutionFacade`；最后删除中央名称分支，不保留能绕过停用的第二入口。第二个迁移对象选不占共享 GUI 的小能力组 | M2 |
| 写操作确认与恢复 | 实现 §8.4 的状态机和绑定参数的确认，做进程死亡故障注入；完成"截图 → 日历"的真机闭环 | 内置能力迁移 |
| 本机 stdio MCP | 宿主在 Alpine/Debian 环境中拉起子进程，管理启停、崩溃重启和资源上限。先看回环过渡路径的实际使用情况再定 | M2 |
| Theta 作为 MCP 服务端 | 把精选的手机工具暴露给用户自己的 Agent（例如电脑上的编码 Agent），走 Tailscale + bearer，手机端逐个工具授权，复用同一套 `PluginPolicy`。难点是后台唤醒，可能需要推送通道 | M2 |
| 独立插件 APK | 只有出现"必须在手机上运行、必须由第三方提供、MCP 做不到"的需求时才评估。走带 UID 校验的绑定服务，不加载外部 DEX | 有真实需求 |

### 13.6 上游同步

改名提交（`2295bb8a`）把所有源文件都移到了 `io/github/bytejuno/theta/` 下。之后再合并上游时会出现三种情况：

- git 的重命名检测能把上游对已有文件的修改带到新路径；
- 涉及 import 的改动容易冲突；
- 上游新增的文件仍然声明旧包名，需要在合并后统一改写 `package` 和 `import`，再编译。

建议：

- 自动合并流程增加一步：合并 → 改写包名 → CI。
- 插件代码放在新包里，对上游热点文件只改组合入口（§4.7）。
- 等内置能力迁移开始大改 `AgentLocalTools` 时，再决定是否停止跟随上游。

## 14. 验收矩阵

| 场景 | 必须满足 | 阶段 |
|---|---|---|
| 外部新增工具 | 同一个 APK 能发现并调用新工具，没有为这个工具名写专用代码 | M1 |
| 同服务双连接 | 凭据、授权、结果和代次分别绑定到各自的 connectionId | M1–M2 |
| 工具定义变更 | 变更后不可用，复核后恢复；描述变化同样展示差异 | M1 |
| 自动任务 | 未放行的连接被拒绝；读过敏感数据后不能调用第三方连接 | M1 |
| 子代理 / 角色会话 | 不能扩大父级或入口已有的权限 | M1 |
| 名称冲突 / 保留名 | 拒绝冲突的注册，不覆盖、不误路由 | M1 |
| batch 子调用 | 每一项都经过相同的接纳和策略检查，被拒绝后不落到旧分支 | M1 |
| 旧配置升级 | 已关闭的工具组仍然关闭；MCP 授权集合不扩大；已启用的工具不失效 | M1 |
| 旧会话记录 | 不改写历史，不因名称迁移出现未知调用 | M1 |
| 超时 / 未知副作用 | 返回 `OPERATION_UNCONFIRMED`，不自动重放写操作 | M1 |
| 停用与接纳竞态 | 能证明一个明确的先后顺序；已经开始的操作不报"未执行" | M2 |
| 停用后重启 / 重新启用 | 旧快照不复活，持久状态一致 | M2 |
| 修改 URL / 账户 / 工具定义 | 旧 run 不会静默发往新目的地 | M2 |
| 连接生命周期 | 断网、认证失效、停用、清理失败可以区分；重启后不伪装在线 | M2 |
| 并行与预算 | 不突破连接串行和已有的目录、响应上限；显示被预算挤掉的工具数 | M2 |
| 账户歧义 | 先澄清或使用显式的默认值，不猜写入目标 | M3 |
| Skill 组合 | 只使用已有的授权；缺少连接或权限被撤销时不自动扩权 | M3 |
| 真实外部兼容 | 非 Theta 定制的服务要记录版本和限制，不能只凭夹具就宣称兼容 | M3 |
| OAuth | PKCE、resource、刷新、scope 不足、撤销分别验证 | M4 |
| 日志 / 导出 / IPC | token 不泄露；敏感的原始结果不进入持久的工具记录 | 全程 |
| 界面缺能力 | 显示具体原因，不把权限不足说成服务器故障 | 全程 |

测试分层：

- 纯 JVM 测试：注册、策略和映射；
- Robolectric 测试：数据迁移和 Android 边界；
- MockWebServer 夹具：双账户和故障注入；
- 兼容实测：非 Theta 定制的真实服务；
- 真机测试：权限撤销、Root 与非 Root、后台运行和进程被杀。

## 17. 参考

调研日期为 2026-11-05。需要说明：

- 下表是各项目官方文档描述的机制，不是本机实测结果，也不是安全审计结论。
- 这些内容可能随版本变化，真正移植前要记录具体版本，并核对许可证。
- 本方案只借鉴架构，不复制代码，也不改变 Theta 作为衍生项目的许可证义务。

| 项目 | 机制 | Theta 采用 | 不照搬 |
|---|---|---|---|
| Operit | ToolPkg 清单，可扩展工具、页面和 hooks，另有 MCP 与 Skills | 统一的扩展入口；连接、指导内容和配置可以组合 | 首版不做 JS、原生桥接和 UI DSL；有文档不等于隔离已经验证 |
| Home Assistant | 集成实现与 config entry 分离；持久配置与 runtime_data 分离；有加载、卸载、迁移状态 | connectionId、明确的生命周期、失败分类 | 不引入实体平台，不把生命周期当作权限沙箱 |
| Pi | 小核心、注册工具、执行事件与取消；扩展状态与模型上下文分开 | 精简核心，由宿主掌握状态 | 进程内扩展会继承宿主权限，不能作为第三方代码的隔离方案 |
| OpenClaw | 静态 manifest、配置 schema、UI hints；安装与启用分离 | 宿主生成有限的配置表单，配置与授权分开 | 不开放大范围的 hooks；不要求 MCP 服务适配私有 manifest |
| DroidRun / Mobilerun | 设备 Portal、UI 层级与截图、应用指导；有直接执行和先规划再执行两条路径 | GUI 作为补充，应用经验放进 Skill | 主机侧框架不等于手机内的 Agent；不引用宣传指标 |

关键决策记录：

1. 用第三方接入来验收"可插拔"，不用迁移内置函数来代替。
2. 以连接实例作为管理和授权的单位。
3. 统一入口，但协议和生命周期按形态区分，不追求包格式大一统。
4. 静态描述和宿主生成的表单优先；任意代码、UI 和 hooks 延后。
5. 核心不随业务扩张：Skill 负责说明方法，工具负责执行，宿主掌握授权和取消。
6. 先补现存缺口（自动任务、定义变更），再增加新能力。
7. 接入外部连接，必须同时加上外发规则。
8. 以真实的操作证据和故障测试来验收，不以模型输出的"完成"文本或宣传数字来验收。
